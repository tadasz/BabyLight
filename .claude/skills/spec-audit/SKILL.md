# Spec-drift auditor

Walk the feature folders under `specs/features/*`, check each against the code it claims to
describe, and write one structured report to `specs/drift-report.md`. Per CLAUDE.md §1 the feature
folder is the source of truth for *how a capability works now* — **drift is a bug**. You find it;
you don't fix it.

**Read-only on all code and on the feature folders.** The only file you write is
`specs/drift-report.md` — no Swift edits, no README/metadata/changelog "corrections". The human
decides whether a finding becomes a `/spec-bug`, a metadata fix, or a changelog line.

Input: `$ARGUMENTS`

## Step 1 — Resolve scope

A named feature (folder or bare slug) → audit only it. Empty or `all` → every `specs/features/*/`
folder. Unknown slug → list the available slugs and stop. Zero feature folders exist → say so and
stop (nothing to audit; folders accumulate organically).

## Step 2 — Deterministic checks (inline, no script)

For each in-scope feature, verify with `ls`/`find`/`git log` (cheap, no subagent):

- every path in `metadata.yaml` → `files:` exists;
- every target in `targets:` is one of `Baby Night Light` / `Baby Light Watch App`;
- `changelog.md` is non-empty and its last entry is not older than the last merged change to the
  feature's claimed files (`git log -1 --format=%as -- <paths>`);
- every spec slug listed in `metadata.yaml` → `specs:` resolves to a real folder.

These are 🟡/🟢 findings for the merged report.

## Step 3 — Load context once

Read once (not per feature): the three constitution files, `CLAUDE.md`, and
`specs/features/README.md` (the contract every folder is held to).

## Step 4 — Semantic pass: ONE SUBAGENT PER FEATURE (mandatory for >1 feature)

**The main thread should not read feature *code* directly when auditing multiple features** — spawn
one `Explore` subagent per in-scope feature, batched 4–5 at a time, each with a self-contained
prompt (for a single small feature, reading inline is acceptable):

- The slug + absolute paths to its `README.md`, `metadata.yaml`, `changelog.md`; the `files:` it
  claims; the deterministic findings already known (don't re-report).
- The task: *read the README + metadata, then the actual Swift at the claimed paths (+ obvious
  neighbours); judge whether the code still matches the claims — focus on **Invariants**,
  **User-facing behaviour**, **state/persistence**, **Where the code lives**; note obvious orphan
  code in the feature's area that `metadata.yaml` doesn't claim. Return ONLY a compact findings
  list — never echo file contents.*
- Return shape, one line per finding: `<severity> | <kind> | <feature> | <detail> | <file:line> | <fix>`,
  severity ∈
  - 🔴 **invariant broken / behaviour mismatch** — the README states something the code no longer
    does. The high-value signal — likely a real bug.
  - 🟡 **stale reference** — a cited path/symbol/identifier moved or renamed.
  - 🟢 **doc lag / orphan** — changelog behind, wording drift, unclaimed code.
- `NONE` if consistent — but never from the README alone; evidence must come from code the subagent
  read.

## Step 5 — Merge & classify

Combine Step 2 + Step 4 findings; de-duplicate (prefer the richer); sort 🔴 → 🟡 → 🟢, then by slug.
Every finding carries concrete `file:line` evidence + a one-line next step.

## Step 6 — Write `specs/drift-report.md`

Overwrite with exactly:

```
# Spec drift report

**Generated:** <YYYY-MM-DD>
**Scope:** <all N features | feature-slug>
**Findings:** 🔴 <n> · 🟡 <n> · 🟢 <n>

> Generated by `/spec-audit`. The feature folder is the source of truth for how a capability works now
> (CLAUDE.md §1). Drift is a bug — fix the code or the spec, don't ignore it.

## 🔴 Behavioural drift (likely bugs)
- **<feature>** — <detail>
  - evidence: `<file:line>`
  - fix: <next step — usually `/spec-bug <description>`>

## 🟡 Stale references
- **<feature>** — <detail> · evidence: `<path | file:line>` · fix: <update citation>

## 🟢 Doc lag & orphans
- **<feature>** — <detail> · evidence: `<path>` · fix: <changelog line / metadata path>

## Clean
<features with no findings, comma-separated — or "none">
```

Zero findings → still write the file (sections `_none_`, counts 0) — a clean report is itself the
signal. Don't stage or commit unless asked.

## Step 7 — Summarise

Counts, the headline 🔴 items with their `/spec-bug` follow-ups, and the report path. Don't paste
the report back.

## Guardrails

- **Read-only on code and feature folders**; sole writable artifact is `specs/drift-report.md`.
- **Never fix drift inline** — 🔴 → `/spec-bug` triage; 🟡/🟢 → human spec edits. Asked to fix
  mid-audit → stop the audit and exit.
- **Never run destructive git, never invent findings** — every line needs `file:line` evidence a
  human can open.
